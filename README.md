# ChronoAccess: Scheduled IAM User Cleanup

[![ci](https://github.com/nerminekabadou/Automated-AWS-Access-Management/actions/workflows/terraform.yml/badge.svg?branch=Scheduled-Cleanup)](https://github.com/nerminekabadou/Automated-AWS-Access-Management/actions/workflows/terraform.yml)

This branch contains the **expiry and cleanup** part of ChronoAccess. Temporary IAM users (interns, contractors) are registered with an end date. Every day, an EventBridge schedule finds the users whose access has expired and emails an admin, who decides with one click whether to **disable** or **delete** each user. The request workflow itself is on [`main`](https://github.com/nerminekabadou/Automated-AWS-Access-Management).

## Architecture

```
EventBridge rate(1 day)
   └─▶ Lambda iam-cleanup-scheduler ──scan──▶ DynamoDB IAMUsersTable (end_date <= today)
          └─▶ SES templated email to the admin with two signed links
                 │
   admin clicks  ▼
GET /decision?username=…&action=disable|delete&expires=…&token=…
   └─▶ API Gateway (HTTP API) ─▶ Lambda iam-admin-action ── verifies the HMAC signature and expiry
          └─▶ async invoke ─▶ Lambda iam-cleanup-lambda
                 disable: deactivate access keys, remove console access
                 delete:  remove keys, MFA, policies and groups, then delete the user
                 └─▶ status updated in DynamoDB (disabled / deleted)
```

### Security choices
- **Signed, expiring links.** The decision endpoint has to be public, because the admin opens it from an email. Every link therefore carries an HMAC-SHA256 signature over `(username, action, expiry)`. A forged or modified link is rejected with HTTP 403, and links expire after `link_ttl_hours` (24 by default). The signing secret is generated by Terraform (`random_password`).
- **Least privilege.** The Lambda role can only touch its own DynamoDB table, invoke the cleanup function, send email from the configured sender, and perform the specific IAM actions needed to clean up users in its own account.
- No account ID or email address is hard-coded. They come from the provider identity and from variables.

## Deploy
```bash
cp terraform.tfvars.example terraform.tfvars   # admin_email, from_email, region
terraform init
terraform apply
```
SES sends a verification email to `from_email`. In the SES sandbox, `admin_email` must be verified as well. Then register users in the table, for example:

```bash
aws dynamodb put-item --table-name IAMUsersTable \
  --item '{"username": {"S": "intern-42"}, "end_date": {"S": "2026-09-30"}, "status": {"S": "active"}}'
```
